# OpenWorkspace 技术方案

## 1. 方案目标

OpenWorkspace 是一个由文件内容驱动的个人网站框架。首要设计目标是让内容使用者只维护私有的 `workspace/`，不需要了解页面组件、路由和构建逻辑。

使用者的标准工作流：

1. 在 `workspace/modules/` 下添加或修改模块。
2. 编写模块 `config.json`。
3. 添加 Markdown、HTML、图片等内容。
4. 执行 `npm run dev` 本地预览。
5. 提交代码，由 CI 执行 `npm run build` 并部署 `dist/`。

`src/` 是框架实现，普通内容使用者不需要修改。`dist/` 是构建产物，不进入版本控制。

## 2. 总体技术路线

第一阶段采用静态站点生成架构：

- Astro：页面模板、静态路由、Markdown Content Collections 和构建。
- TypeScript：配置模型、内容加载器、目录树和路由生成。
- Zod：构建期配置校验。
- 原生 CSS：桌面和移动端响应式布局。
- 原生客户端 TypeScript：移动端抽屉和边缘滑动交互。
- Vitest：配置及内容加载逻辑单元测试。
- Playwright：后续加入页面路由和移动端交互测试。

纯静态模块不需要数据库和常驻后端。需要动态数据的模块通过 `runtime: "server"` 注册私有 API；认证与真正的私有页面仍需在服务端访问控制完成。

## 3. 架构与数据流

```text
workspace/
  config.json
  modules/<module>/config.json
  modules/<module>/content/**/*
          │
          ▼
配置与内容加载器
  - 扫描一级模块目录
  - 校验 JSON 配置
  - 限制文件访问范围
  - 生成模块清单
  - 生成目录树
  - 生成内容路由
          │
          ▼
Astro 通用页面模板
  - 模块导航
  - 目录树
  - Markdown 渲染
  - HTML 沙箱
          │
          ▼
dist/ 静态网站

workspace/services/ + modules/*/server/
          │
          ▼
src/server 通用 HTTP 宿主
          │
          ▼
Nginx /api/ 与 /openworkspace-admin/ 反向代理
```

这里不通过代码生成器向 `src/pages/` 写入大量页面文件。`src/pages/[module]/[...slug].astro` 是框架内置的通用模板，构建时使用 `getStaticPaths()` 根据 `workspace/modules/` 清单生成最终 URL。

这种方式避免生成代码与内容不同步，也避免每次新增文章都产生待清理的中间源码。

## 5. 配置规范

### 5.1 网站配置

`workspace/config.json`：

```json
{
  "title": "OpenWorkspace",
  "description": "由内容驱动的个人网站",
  "defaultModule": "introduction"
}
```

`defaultModule` 必须指向一个存在的公开模块。默认模块放在全局配置中，避免多个模块同时声明自己为默认模块。

### 5.2 模块配置

`workspace/modules/<module>/config.json`：

```json
{
  "id": "articles",
  "title": "文章",
  "order": 20,
  "access": "public",
  "runtime": "static",
  "icon": "./icon.svg",
  "contentDir": "./content",
  "showDirectoryTree": true,
  "index": "index.md"
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 模块稳定标识，只允许小写字母、数字和连字符，必须与目录名一致 |
| `title` | string | 模块显示标题 |
| `order` | integer | 导航排序，数值越小越靠前 |
| `access` | enum | `public`、`authenticated` 或 `allowlist` |
| `runtime` | enum | `static`、`client` 或 `server`；默认 `static` |
| `serverEntry` | relative path | `server` 模块必填，指向模块私有服务入口 |
| `icon` | relative path | 相对于模块目录的图标路径 |
| `contentDir` | relative path | 相对于模块目录的内容目录 |
| `showDirectoryTree` | boolean | 是否展示内容目录树 |
| `index` | relative path | 相对于模块目录的首页，默认 `index.md`，也可指向 `content/` 内文件 |

配置文件使用严格 JSON，不允许注释、尾逗号或中文标点。需要解释字段时统一写在本文档中。

所有配置路径都经过边界检查，不允许使用绝对路径或通过 `../` 访问模块目录外的文件。符号链接不参与内容扫描。

## 6. 内容和路由规则

### 6.1 Markdown

Markdown 由 Astro Content Collections 在构建期加载和渲染。支持 Frontmatter：

```yaml
---
title: 第一篇文章
description: 页面摘要
order: 10
draft: false
---
```

第一阶段使用文件名作为目录树标题，页面标题优先使用 Frontmatter 中的 `title`。后续可让目录树也读取 `title` 和 `order`。

### 6.2 URL 映射

路由由文件相对 `contentDir` 的路径生成：

| 内容文件 | 页面 URL |
| --- | --- |
| `articles/index.md` | `/articles/` |
| `articles/content/hello.md` | `/articles/hello/` |
| `articles/content/category/a.md` | `/articles/category/a/` |
| `articles/content/category/index.md` | `/articles/category/` |

访问某一内容 URL 时，目录树自动展开当前文件所在的目录，并标记当前文件。浏览器前进、后退和直接打开 URL 均以路由为准，不依赖只存在于内存中的选中状态。

### 6.3 HTML 工具

HTML 文件不直接注入主页面 DOM，而是通过独立资源路由和带 `sandbox` 的 iframe 加载：

```html
<iframe sandbox="allow-scripts allow-forms allow-downloads"></iframe>
```

当前沙箱不启用 `allow-same-origin`，工具脚本不能直接访问主页面上下文。资源响应附带 Content Security Policy 和 `X-Content-Type-Options: nosniff`。

后续如果工具需要多文件资源、网络访问或持久化能力，需要单独设计工具权限清单，不能简单扩大所有 iframe 的权限。

## 7. 页面结构与交互

### 7.1 桌面端

- 左侧固定模块导航。
- 有目录树的模块在内容区域左侧增加二级栏。
- 右侧为 Markdown 或 HTML 内容。
- 当前模块和当前内容均通过 `aria-current="page"` 标记。

### 7.2 移动端

- 顶部提供明确的菜单按钮，不能只依赖滑动手势。
- 模块导航从左侧以抽屉形式出现。
- 支持屏幕左侧向右滑动打开。
- 支持遮罩点击和 Escape 键关闭。
- 用户启用“减少动态效果”时取消动画。

第一阶段移动端目录树位于内容上方，并限制最大高度。后续内容数量增大时，可以改为独立的二级抽屉。

## 8. 私有模块设计边界

当前静态版本只构建 `access: "public"` 的模块。`authenticated` 和 `allowlist` 模块不会生成导航、页面或公开资源路由。

设备白名单不能作为可靠的访问控制：浏览器不存在通用、稳定且不可伪造的设备 ID；仅在前端隐藏导航也无法保护已经发布的静态文件。

私有模块第二阶段方案：

1. 使用 Astro Cloudflare、Vercel 或 Node Adapter 启用按需服务端渲染。
2. 使用登录账户、Passkey 或外部身份提供方完成身份认证。
3. 在服务端 Middleware 中校验会话和用户白名单。
4. 私有 Markdown 和附件只从受保护的服务端路由返回，不进入公开 `dist/`。
5. 使用签名且设置 `HttpOnly`、`Secure`、`SameSite` 的会话 Cookie。

如果所谓“私有”只是同一用户不同浏览器的界面偏好，可以使用签名 Cookie，但必须明确它不构成内容安全保护。

## 9. 构建与部署

运行环境：

- Node.js `>= 22.22.2`
- npm `>= 10.0.0`

常用命令：

```bash
npm install
npm run dev
npm run check
npm test
npm run build
npm run preview
npm run api
```

不启用私有服务时，静态输出可以部署到 GitHub Pages、Cloudflare Pages、Netlify、Vercel 或普通静态服务器。启用动态模块或重新生成服务时，Nginx 提供 `dist/` 并把 API 路径反向代理到只监听回环地址的 `npm run api`。CI 推荐按以下顺序执行：

```text
npm ci → npm run check → npm test → npm run build → 发布 dist/
```

内容修改必须触发重新构建。工具栏“重新生成”通过受保护的私有服务依次执行 `git pull --ff-only` 和 `npm run build`；动态数据保存在 `workspace/storage/`，不得复制进 `dist/`。

## 10. 测试策略

单元测试重点：

- 全局和模块配置默认值。
- 非法 JSON、非法模块 ID 和路径逃逸。
- 模块排序和默认模块校验。
- 文件路径到 URL 的映射。
- 嵌套目录树生成。
- 非公开模块不进入静态路由。

端到端测试重点：

- 首页进入默认模块。
- 模块切换与浏览器前进、后退。
- 直接打开嵌套文章 URL。
- 当前目录自动展开。
- 移动端按钮、滑动、遮罩和 Escape 关闭抽屉。
- HTML 工具能运行，但不能访问主页面 DOM。

## 11. 第一阶段完成标准

- 使用者新增模块或内容时只修改 `workspace/modules/`。
- 构建自动生成导航、目录树和独立 URL。
- Markdown 与单文件 HTML 能正确展示。
- 桌面端与移动端布局符合设计文档。
- 配置错误在构建阶段给出明确错误，而不是产生残缺页面。
- 非公开模块不进入静态构建结果。
- 单元测试、类型检查和生产构建全部通过。
