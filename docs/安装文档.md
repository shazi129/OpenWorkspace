# OpenWorkspace 安装与内容创作指南

本文面向 OpenWorkspace 的内容维护者和首次参与开发的工程人员，包含 Windows、Linux、macOS 环境安装、工程初始化、模块配置、文章编写和发布前检查。

OpenWorkspace 的页面在构建期生成到 `<distRoot>/`：日常内容维护只需修改当前工作区的 `modules/`，运行开发服务器预览，构建后发布生成目录。仓库内 `workspace/` 和框架根目录 `dist/` 分别是默认工作区与默认生成目录，`themes/normal/` 是默认主题；三者通过 `openworkspace.config.json` 选择。`src/` 是公开框架实现；需要动态 API 时，由所选工作区中的私有服务配合常驻 Node.js 进程提供。

## 1. 环境要求

| 软件 | 要求 | 用途 |
| --- | --- | --- |
| Node.js | `>= 22.22.2`，推荐 24.x LTS | 运行 Astro、TypeScript 和测试工具 |
| npm | `>= 10.0.0` | 安装依赖和执行工程命令，随 Node.js 安装 |
| Git | 建议安装当前稳定版 | 获取源码和提交内容 |
| 编辑器 | VS Code、WebStorm 等，任选 | 编辑 Markdown、JSON、HTML |

不要单独全局安装 Astro、TypeScript 或 Vitest。工程已在 `package.json` 和 `package-lock.json` 中锁定所需依赖，安装本地依赖即可。

安装完成后，所有平台都应能执行：

```text
node --version
npm --version
git --version
```

其中 Node.js 版本不能低于 `v22.22.2`，npm 主版本不能低于 10。

## 2. Windows 环境安装

### 2.1 安装 Git

从 [Git for Windows](https://git-scm.com/install/windows.html) 下载并运行安装程序。安装过程可以保留默认选项，但需确保 Git 被加入 `PATH`。

Windows 10/11 也可以在 PowerShell 中使用 `winget`：

```powershell
winget install --id Git.Git -e --source winget
```

### 2.2 安装 Node.js

推荐使用 fnm（Fast Node Manager）管理 Node.js 版本，这样可以与项目自带的 `scripts/preview.bat` 和 `.nvmrc` 配合，自动切换到工程所需版本。

#### 方式一：通过 fnm 安装（推荐）

安装 fnm：

```powershell
winget install Schniz.fnm
```

安装后重新打开终端，然后安装并激活工程所需的 Node.js 版本：

```powershell
fnm install 22.22.2
fnm use 22.22.2
```

验证安装：

```powershell
node --version
npm --version
```

此后在工程根目录运行 `scripts\preview.bat` 时，脚本会自动读取 `.nvmrc` 并切换到 `22.22.2`。

#### 方式二：通过官网安装包安装

1. 打开 [Node.js 下载页](https://nodejs.org/en/download)。
2. 选择 24.x LTS 的 Windows Installer（`.msi`），并根据设备选择 x64 或 ARM64。
3. 运行安装程序，保留 npm 和"添加到 PATH"选项。
4. 关闭并重新打开 PowerShell 或 Windows Terminal。

验证安装：

```powershell
node --version
npm --version
git --version
```

如果 PowerShell 提示无法运行 `npm.ps1`，可以先用 `npm.cmd` 代替 `npm`，也可以在"命令提示符"中执行相同的 npm 命令。这不影响工程本身。

## 3. Linux 环境安装

推荐使用 nvm 管理 Node.js，这样可以避免系统软件源中的 Node.js 版本过旧，也不会把 npm 依赖安装到系统目录。

### 3.1 安装 Git 和 curl

Debian / Ubuntu：

```bash
sudo apt update
sudo apt install -y git curl
```

Fedora / RHEL：

```bash
sudo dnf install -y git curl
```

Arch Linux：

```bash
sudo pacman -S --needed git curl
```

### 3.2 安装 nvm 和 Node.js

以下命令使用 nvm `v0.40.4`。执行远程安装脚本前，可先到 [nvm 官方仓库](https://github.com/nvm-sh/nvm) 核对当前版本和脚本内容。

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.4/install.sh | bash
```

关闭并重新打开终端，然后执行：

```bash
command -v nvm
nvm install 24
nvm alias default 24
node --version
npm --version
git --version
```

如果提示 `nvm: command not found`，先重新打开终端；仍未生效时，按照安装脚本最后的提示加载 `~/.bashrc`、`~/.zshrc` 或 `~/.profile`。

## 4. macOS 环境安装

### 4.1 安装 Git

在 Terminal 中执行：

```bash
xcode-select --install
```

这会安装 Apple Command Line Tools 和 Git。如果已使用 Homebrew，也可以执行 `brew install git`。

### 4.2 安装 nvm 和 Node.js

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.4/install.sh | bash
```

关闭并重新打开 Terminal，然后执行：

```bash
command -v nvm
nvm install 24
nvm alias default 24
node --version
npm --version
git --version
```

Intel Mac 和 Apple Silicon Mac 均可使用 Node.js 24。nvm 会自动选择与当前设备架构匹配的版本。

如果不希望使用版本管理器，也可以从 [Node.js 下载页](https://nodejs.org/en/download) 安装 24.x LTS 的 macOS Installer（`.pkg`）。

## 5. 获取源码并初始化工程

### 5.1 克隆仓库

将下面的 `YOUR_REPOSITORY_URL` 替换为实际仓库地址：

```bash
git clone YOUR_REPOSITORY_URL OpenWorkspace
cd OpenWorkspace
```

如果使用下载的源码压缩包，解压后在终端进入包含 `package.json` 的项目根目录即可。

### 5.2 选择工作区、生成目录与主题

根目录的 `openworkspace.config.json` 默认指向仓库内示例：

```json
{
  "workspaceRoot": "./workspace",
  "distRoot": "./dist",
  "theme": "normal"
}
```

要把真实数据和生成物放在独立目录或私有仓库中，可同时修改 `workspaceRoot` 和 `distRoot`。两个相对路径都以 OpenWorkspace 框架仓库根目录为基准，例如两个仓库并列时：

```json
{
  "workspaceRoot": "../MyWorkspace",
  "distRoot": "../MyWorkspace/dist",
  "theme": "dark"
}
```

也可以填写绝对路径。配置文件不存在，或其中的 `workspaceRoot` 不存在/不是目录时，会从 OpenWorkspace 根目录回退到内置 `workspace/`；框架根目录 `dist/` 和 `normal` 主题仍分别是默认生成目录和主题。只省略 `distRoot` 或 `theme` 时分别默认使用 `./dist` 或 `normal`。部署环境可用 `OPENWORKSPACE_WORKSPACE_ROOT` 覆盖工作区。JSON 无法解析、字段未知或字段值格式无效时，命令仍会直接报错，不会静默回退。

内置主题位于 `themes/normal/theme.css` 和 `themes/dark/theme.css`。`normal` 保持原来的浅色外观，`dark` 使用深褐背景和暖色文字。新增主题时复制一个主题目录、完整保留变量并修改取值，然后把 `theme` 改成新目录名；名称只能使用小写字母、数字和连字符。切换主题后需要重启 `npm run dev` 或重新运行构建。

构建会管理并清理生成目录，因此 `distRoot` 不能填写框架根目录、工作区根目录、它们的父目录，或 `src`、`modules`、`services`、`storage`、`deploy` 等源码与私有数据目录。若输出到另一个 Git 仓库，请在该仓库中忽略生成目录。

### 5.3 安装依赖

首次初始化或 CI 环境使用：

```bash
npm ci
```

`npm ci` 会严格按照 `package-lock.json` 安装，结果更稳定。只有在主动添加、升级或删除依赖时才使用 `npm install`，并同时提交更新后的 `package.json` 和 `package-lock.json`。

### 5.4 完成首次检查

```bash
npm run check
npm test
npm run build
```

三条命令都成功后，初始化完成。生产构建位于配置的 `<distRoot>/`（默认 `dist/`），该目录由构建生成，不应手工编辑或提交到版本控制。

### 5.5 启动本地预览

```bash
npm run dev
```

终端会显示本地地址，默认通常是 `http://localhost:4321/`。保持命令运行，在浏览器中打开该地址；修改内容后页面会自动刷新。

如需让同一局域网中的其他设备访问：

```bash
npm run dev -- --host
```

完成生产构建后，可用以下命令预览 `<distRoot>/` 的最终结果：

```bash
npm run preview
```

## 6. 初始化站点内容

内容目录的基本结构如下：

```text
<workspaceRoot>/
├── config.json
├── modules/
│   ├── introduction/
│   │   ├── config.json
│   │   ├── icon.svg
│   │   ├── index.md
│   │   └── content/
│   ├── articles/
│   │   ├── config.json
│   │   ├── icon.svg
│   │   ├── index.md
│   │   └── content/
│   │       └── 示例分类/
│   │           └── 第一篇文章.md
│   ├── tools/
│   │   ├── config.json
│   │   ├── icon.svg
│   │   └── content/
│   │       └── index.html
├── services/                    # 跨模块私有服务
├── storage/                     # 数据库、缓存和任务状态
└── deploy/                      # 当前实例的部署配置
    ├── nginx/openworkspace.conf
    └── systemd/openworkspace-api.service
```

### 6.1 配置站点信息

编辑 `<workspaceRoot>/config.json`。使用默认示例时，该文件就是 `workspace/config.json`：

```json
{
  "title": "OpenWorkspace",
  "description": "由内容驱动的个人网站",
  "defaultModule": "introduction"
}
```

| 字段 | 说明 |
| --- | --- |
| `title` | 站点名称，显示在页面和浏览器标题中 |
| `description` | 站点描述，用作页面的 description 元数据 |
| `defaultModule` | 打开站点首页时进入的模块 ID，必须指向一个存在的 `public` 模块 |

配置文件是严格 JSON：不能写注释、尾逗号或中文标点，字符串必须使用双引号。

### 6.2 新建模块

下面以新建 `notes` 模块为例。

Windows PowerShell：

```powershell
New-Item -ItemType Directory -Force workspace\modules\notes\content
Copy-Item workspace\modules\articles\icon.svg workspace\modules\notes\icon.svg
```

Linux / macOS：

```bash
mkdir -p workspace/modules/notes/content
cp workspace/modules/articles/icon.svg workspace/modules/notes/icon.svg
```

创建 `workspace/modules/notes/config.json`：

```json
{
  "id": "notes",
  "title": "笔记",
  "order": 4,
  "access": "public",
  "private": false,
  "publish": true,
  "runtime": "static",
  "icon": "./icon.svg",
  "contentDir": "./content",
  "showDirectoryTree": true
}
```

如果需要完全自定义模块首页，再创建 `workspace/modules/notes/index.md`：

```markdown
---
title: 笔记
description: 笔记模块首页
---

# 笔记

从左侧目录选择一篇笔记。
```

这一步可以省略。配置中没有 `index`，并且模块根目录也没有 `index.md` 时，OpenWorkspace 会自动生成按创建时间排序的分页首页，并提供标题和标签搜索。

模块字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 模块稳定标识，只允许小写字母、数字和连字符，且必须与模块目录名一致 |
| `title` | 导航中显示的模块名称 |
| `order` | 非零整数；正数 `1、2、3` 从顶部向下，负数 `-1、-2、-3` 从底部向上 |
| `access` | `public`、`authenticated` 或 `allowlist`；当前静态版本只构建 `public` 模块 |
| `private` | 是否隐藏桌面和移动端工具栏入口，默认 `false`；隐藏后仍可通过 URL 访问 |
| `publish` | 是否生成页面和资源到 `<distRoot>/`，默认 `true`；设为 `false` 时完全跳过模块 |
| `runtime` | `static`、`client` 或 `server`；默认 `static` |
| `serverEntry` | `runtime` 为 `server` 时必填，指向模块自己的服务入口，例如 `./server/index.mjs` |
| `icon` | 相对于模块目录的图标路径，目标文件必须存在 |
| `contentDir` | 相对于模块目录的内容目录 |
| `showDirectoryTree` | 是否在模块页面显示内容目录树 |
| `index` | 字符串表示相对于模块目录的自定义首页；`{ "type": "generated", "pageSize": 20 }` 强制使用自动首页；省略时优先使用根 `index.md`，不存在则自动生成 |

配置中的路径不能是绝对路径，也不能用 `../` 越过模块目录。符号链接不会参与内容扫描。

需要强制使用自动首页或调整分页大小时，可以配置：

```json
{
  "index": {
    "type": "generated",
    "pageSize": 20
  }
}
```

`pageSize` 允许 `1` 到 `100`。自动首页使用 `?q=关键词&tag=标签&page=2` 保存搜索和分页状态；每个公开发布模块还会生成 `/openworkspace-index/<module>.json`，其中只包含标题、链接、内容类型、创建时间和标签，不包含正文。

`authenticated` 和 `allowlist` 是后续服务端认证阶段预留的访问级别。当前版本会把这些模块完全排除在导航、页面和静态资源之外，并不会生成一个可登录访问的私有页面。

`private` 只控制导航可见性，不是访问控制。例如下面的模块不会显示在工具栏，但任何知道 `/notes/` 的访问者都能打开它：

```json
{
  "private": true,
  "publish": true
}
```

敏感模块应使用 `publish: false`，或等待 `authenticated`、`allowlist` 对应的服务端认证能力，不能仅依赖隐藏入口。

## 7. 编写 Markdown 文章

### 7.1 创建文章文件

在目标模块的 `content/` 中创建 `.md` 文件。例如：

```text
workspace/modules/articles/content/开发指南/环境配置.md
```

推荐使用 UTF-8 编码。一个完整的文章模板如下：

````markdown
---
title: 环境配置
description: Windows、Linux 和 macOS 的开发环境准备
create: 2026-08-08 15:30:00
tags: 开发指南,环境配置
order: 10
draft: false
---

# 环境配置

这里写文章摘要或引言。

## 安装 Node.js

正文支持常用 Markdown 语法。

### 示例命令

```bash
node --version
npm --version
```

## 参考资料

- [Node.js](https://nodejs.org/)
- [Astro](https://astro.build/)
````

Frontmatter 必须位于文件开头，并由两行 `---` 包围。当前支持的字段为：

| 字段 | 类型 | 当前行为 |
| --- | --- | --- |
| `title` | string | 作为页面标题和浏览器标签标题；正文中的一级标题仍需自己写 |
| `description` | string | 已进入内容模型，预留作页面摘要；当前页面元数据仍使用站点描述 |
| `create` | datetime | 文章创建时间；目录树和自动首页按该时间从近到远排列，缺少或为空时使用 2000-01-01 |
| `tags` | string 或 string[] | 文章标记；支持逗号分隔、数组、缺省值和空值，自动首页可按标签搜索与筛选 |
| `order` | integer | 已校验，但当前目录树尚未按此字段排序 |
| `draft` | boolean | 默认 `false`；当前尚未根据该字段排除构建 |

重要：`draft: true` 当前不会阻止文章进入 `<distRoot>/`。未准备公开的文章不要放进 `public` 模块，或在发布前把文件移出该模块的 `content/`。

### 7.2 文件名、目录树与 URL

页面 URL 由文件相对于 `contentDir` 的路径生成：

| 内容文件 | 页面 URL |
| --- | --- |
| `articles/index.md` 或自动首页 | `/articles/` |
| `articles/content/hello.md` | `/articles/hello/` |
| `articles/content/category/a.md` | `/articles/category/a/` |
| `articles/content/category/index.md` | `/articles/category/` |

当前目录树有以下规则：

- 同级目录和文章按 `create` 从近到远排列；未填写时间的旧文章使用 2000-01-01。
- 目录时间取其后代文章中最早的 `create`，包括旧文章的默认时间。
- 时间相同时按名称排序。
- 目录名和文件名会直接作为目录树标签；Frontmatter 的 `title` 暂不改变目录树名称。
- 模块根 `index.md` 表示自定义模块首页且不进入目录树；没有该文件时自动生成首页，`content/` 根目录不要放置任何 `index.md`、`index.html` 或 `index.htm`。
- 中文路径可以使用，浏览器会进行 URL 编码；如果 URL 长期对外引用，建议在命名后不要随意改动。
- 重命名或移动文件会改变 URL，旧链接不会自动重定向。

文章之间建议使用站内绝对路径，避免移动当前文章后链接失效：

```markdown
[阅读第一篇文章](/articles/示例分类/第一篇文章/)
```

### 7.3 常用 Markdown 写法

````markdown
# 一级标题
## 二级标题

普通段落，使用 **粗体**、*斜体* 和 `行内代码`。

> 这是一段引用。

- 无序列表
- 第二项

1. 有序列表
2. 第二项

| 名称 | 说明 |
| --- | --- |
| OpenWorkspace | 内容驱动站点 |

```ts
const message: string = "Hello";
console.log(message);
```
````

LaTeX 公式使用 `$...$` 行内写法，或让 `$$` 分隔符单独占行来显示块级公式：

```markdown
质能方程为 $E=mc^2$。

$$
\int_0^1 x^2 \, dx = \frac{1}{3}
$$
```

公式在构建时由 KaTeX 转换，不需要客户端脚本。正文中的美元符号需要转义，例如 `\$100`。

### 7.4 图片和附件

建议把图片放在文章同目录或其子目录，并使用相对于当前 Markdown 文件的路径。构建时 Astro 会解析并优化这类图片：

```markdown
![持仓][holding-image]

[holding-image]: ./持仓.jpg
```

需要设置浮动、尺寸等自定义属性时，也可以让原生 HTML `<img>` 单独占一行：

```html
<img src="./持仓.jpg" alt="持仓" style="width:40%; float:left; margin:10px;" />
```

该写法会在构建阶段转成图片节点，相对路径仍按当前文章目录解析，`alt`、`title`、`style`、`loading` 等属性会被保留。包含其他元素的混合 HTML 片段不会自动转换。

普通附件仍可通过 OpenWorkspace 资源路由引用。例如文件位置为：

```text
workspace/modules/articles/content/attachments/checklist.pdf
```

在文章中写：

```markdown
[下载检查清单](/openworkspace-assets/articles/content/attachments/checklist.pdf)
```

资源 URL 的格式是：

```text
/openworkspace-assets/<模块ID>/<相对于模块目录的文件路径>
```

图片应填写能表达内容的替代文本。不要把敏感文件放进 `public` 模块；该模块中的附件会进入公开构建产物。

## 8. 编写 HTML 工具页面

模块内容也可以是 `.html` 或 `.htm`。例如：

```text
workspace/modules/tools/content/json-formatter.html
```

对应页面 URL 为：

```text
/tools/json-formatter/
```

HTML 页面通过带沙箱限制的 iframe 加载。当前允许脚本、表单和下载，但不允许访问 OpenWorkspace 主页面 DOM，也不启用 `allow-same-origin`。资源响应带有 Content Security Policy，外部网络请求默认不可用。

因此，工具页应优先使用原生 HTML、CSS、JavaScript 和模块内的本地静态资源。简单工具可以写成单个 HTML 文件；使用本地 CSS 或 JavaScript 时，将文件放在同一内容目录并使用相对路径引用。

## 9. 使用 Nginx 部署

OpenWorkspace 的页面仍由 Nginx 直接提供 `<distRoot>/` 中的静态文件。只浏览页面时不需要 Node.js 常驻；如果要使用 `runtime: "server"` 模块或全局服务，则同时运行 `npm run api`，并由 Nginx 把 `/api/` 反向代理到该进程。

以下示例假设：

- 域名为 `example.com`，使用时需替换为实际域名。
- 工程部署目录为 `/opt/openworkspace`，并使用默认 `distRoot: "./dist"`，所以 Nginx 的站点根目录为 `/opt/openworkspace/dist`。修改 `distRoot` 后必须同步修改 Nginx `root`。
- 站点部署在域名根路径 `/`，而不是 `/openworkspace/` 等子路径。

### 9.1 安装 Nginx

Debian / Ubuntu：

```bash
sudo apt update
sudo apt install -y nginx rsync
sudo systemctl enable --now nginx
```

Fedora / RHEL：

```bash
sudo dnf install -y nginx rsync
sudo systemctl enable --now nginx
```

也可以按照 [Nginx 官方 Linux 软件包说明](https://nginx.org/en/linux_packages.html) 配置官方软件源。服务器防火墙和云平台安全组需允许 TCP 80；启用 HTTPS 后还需允许 TCP 443。

### 9.2 构建站点文件

在工程根目录执行：

```bash
npm ci
npm run check
npm test
npm run build
```

如果只部署静态页面，也可以把 `<distRoot>/` 同步到任意专用 Web 目录。需要 API 时，运行服务的专用非 root 用户还应具有所选工作区服务和 `storage/` 所需权限。

在启用了 SELinux 的 Fedora / RHEL 上，可恢复 Web 目录的默认安全上下文：

```bash
sudo restorecon -Rv /opt/openworkspace/dist
```

### 9.3 配置虚拟主机

配置文件位置通常为：

- Debian / Ubuntu 发行版软件包：`/etc/nginx/sites-available/openworkspace`。
- Fedora / RHEL 或 Nginx 官方软件包：`/etc/nginx/conf.d/openworkspace.conf`。

写入以下配置，并把 `example.com` 和 `www.example.com` 替换为实际域名：

默认工作区在 `workspace/deploy/nginx/openworkspace.conf` 提供了同等配置；外部工作区使用相同的 `deploy/nginx/openworkspace.conf` 路径。

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    root /opt/openworkspace/dist;
    index index.html;
    charset utf-8;
    autoindex off;

    # Astro 的自定义 404 页面。
    error_page 404 /404.html;

    location = /404.html {
        internal;
        add_header Cache-Control "no-cache" always;
        add_header X-Content-Type-Options "nosniff" always;
    }

    # 文件名带内容哈希，可以长期缓存。
    location ^~ /_astro/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        add_header X-Content-Type-Options "nosniff" always;
    }

    # 模块图标、图片、附件和 HTML 工具资源。
    location ^~ /openworkspace-assets/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=3600" always;
        add_header X-Content-Type-Options "nosniff" always;
        add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; object-src 'none'; base-uri 'none'" always;
    }

    # 私有服务只监听 127.0.0.1，由 Nginx 对外转发。
    location ^~ /api/ {
        proxy_pass http://127.0.0.1:4174;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 支持 /articles/hello/ 这类目录式静态路由。
    location / {
        try_files $uri $uri/ $uri/index.html =404;
        add_header Cache-Control "no-cache" always;
        add_header X-Content-Type-Options "nosniff" always;
    }

    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types
        text/css
        text/plain
        application/javascript
        application/json
        application/xml
        image/svg+xml;
}
```

该配置的关键点：

- `root` 必须指向 `distRoot` 的实际目录，而不是源码目录。
- `try_files` 会查找实际文件、目录及目录下的 `index.html`，同时让不存在的路径返回真正的 404。
- `/_astro/` 文件带构建哈希，可以安全地设置长期缓存。
- 文章 HTML 使用 `no-cache`，重新发布后浏览器会及时校验新内容。
- `/openworkspace-assets/` 重新补充了 HTML 工具沙箱所需的 CSP 和 `nosniff` 响应头；静态文件部署时不能依赖构建阶段的响应头自动保留。
- `/api/` 只由 Node.js 服务处理；所选工作区的 `services/` 与 `storage/` 绝不能设置为 Nginx 的静态目录。
- 主 Nginx 配置的 `http` 块应包含 `include /etc/nginx/mime.types;`，以便正确返回 CSS、JavaScript、SVG 等文件类型。发行版默认配置通常已经包含它。

如果只通过服务器 IP 访问，可暂时把 `server_name` 写为 `_`，并在两个 `listen` 指令中加入 `default_server`。同时要停用发行版自带的默认站点，确保同一地址和端口没有重复的 `default_server`。正式使用域名后应换成实际域名。

### 9.4 启动私有 API 服务

只部署静态页面时可以跳过本节。服务所需的密钥应写入仅管理员可读的环境文件，不要提交到 Git；宿主本身支持以下环境变量：

```text
OPENWORKSPACE_API_HOST=127.0.0.1
OPENWORKSPACE_API_PORT=4174
```

可使用 systemd 让服务常驻。以下示例假设专用用户为 `openworkspace`：

默认工作区在 `workspace/deploy/systemd/openworkspace-api.service` 提供该配置；外部工作区使用相同路径。

```ini
[Unit]
Description=OpenWorkspace private API
After=network.target

[Service]
Type=simple
User=openworkspace
WorkingDirectory=/opt/openworkspace
EnvironmentFile=/etc/openworkspace/api.env
ExecStart=/usr/bin/npm run api
Restart=on-failure
PrivateTmp=true
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

保存为 `/etc/systemd/system/openworkspace-api.service` 后执行：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now openworkspace-api
curl http://127.0.0.1:4174/health
```

健康检查应返回 `{"status":"ok"}`。服务用户只需拥有框架代码、所选工作区服务和 `storage/` 所需权限，不应使用 root 运行。

### 9.5 启用并检查 Nginx 配置

使用 Debian / Ubuntu 的 `sites-available` 目录时，还需要创建启用链接：

```bash
sudo ln -s /etc/nginx/sites-available/openworkspace /etc/nginx/sites-enabled/openworkspace
```

使用 `/etc/nginx/conf.d/openworkspace.conf` 时不需要创建链接。

检查语法并平滑重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

检查首页、文章、静态资源和 404 状态：

```bash
curl -I http://example.com/
curl -I http://example.com/articles/
curl -I http://example.com/openworkspace-assets/articles/icon.svg
curl -I http://example.com/not-found/
```

前三个请求应返回 `200`；不存在的地址应返回 `404`。还应在浏览器中检查 Markdown 页面、图片和 HTML 工具是否正常显示。

### 9.6 HTTPS 和子路径注意事项

正式公网部署应通过 Certbot、云平台证书服务或其他 ACME 客户端申请证书，并把 HTTP 重定向到 HTTPS。私钥只能保存在服务器的受限目录中，不能提交到 Git 仓库；同时应确认续期任务能够自动运行。

当前工程生成的导航和资源地址都以 `/` 开头，因此上述配置按域名根路径部署。如果必须部署到 `https://example.com/openworkspace/`，需要先在 `astro.config.mjs` 中配置匹配的 `base` 并重新构建，不能只在 Nginx 中增加一个 `location` 前缀。

如果向公网开放 API，必须启用 HTTPS，并根据具体服务增加认证；还应在 Nginx、VPN 或防火墙层限制敏感接口来源。

## 10. 日常写作与发布流程

推荐每次内容修改都遵循以下流程：

1. 拉取仓库的最新变更。
2. 只在所选 `<workspaceRoot>/modules/` 下添加或修改模块、文章和附件。
3. 运行 `npm run dev`，检查桌面端和移动端显示、链接、图片及目录树。
4. 运行类型检查、测试和生产构建。
5. 检查 Git 变更，提交并推送；由 CI 发布 `<distRoot>/`。

```bash
git pull --ff-only
npm run check
npm test
npm run build
git status
git add workspace/modules
git commit -m "content: 更新文章"
git push
```

如果本次还修改了说明文档，应把对应文档路径一并加入 `git add`。不要执行 `git add dist`。

CI 推荐顺序：

```text
npm ci → npm run check → npm test → npm run build → 发布 <distRoot>/
```

## 11. 常见问题

### Node.js 版本不满足要求

看到 `Unsupported engine` 或类似提示时，先运行 `node --version`。nvm 用户可执行：

```bash
nvm install 24
nvm use 24
```

然后重新执行 `npm ci`。

### 配置修改后构建失败

重点检查：

- JSON 是否使用双引号，是否包含注释或尾逗号。
- 模块目录名是否与 `id` 完全一致。
- `defaultModule` 是否指向一个 `public` 模块。
- `icon`、`contentDir` 和字符串形式的 `index` 指向的文件或目录是否存在；省略 `index` 且没有根 `index.md` 时会自动生成首页。
- `id` 是否只包含小写字母、数字和连字符。

构建会主动拒绝无效配置，不会生成内容不完整的页面。

### 新文章没有出现在目录树

确认文件位于模块配置指定的 `contentDir` 中，扩展名为 `.md`、`.html` 或 `.htm`，并且该模块设置了 `"showDirectoryTree": true`。符号链接和其他扩展名不会作为页面显示。

### 本地端口被占用

指定其他端口：

```bash
npm run dev -- --port 4322
```

### 修改 `workspace/modules/` 后线上没有变化

OpenWorkspace 是静态站点，内容修改必须重新执行 `npm run build` 并重新发布 `<distRoot>/`。把文件上传到源码目录并不会自动改变已经发布的站点。
